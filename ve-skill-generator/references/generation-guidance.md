## 1. Description Optimization (Trigger Accuracy)

The `description` field in frontmatter is the sole trigger mechanism for skill activation. An under-specified description means the skill won't load when it should; an over-broad one means it loads when it shouldn't. Optimize it systematically:

### Write an Effective Description

Follow these principles from the [agentskills.io specification](https://agentskills.io/specification):

| Principle | Guideline | Example |
|-----------|-----------|---------|
| **Imperative phrasing** | Frame as instruction to agent: "Use when..." | `Use when the user needs to...` |
| **Focus on user intent** | Describe what user is trying to achieve, not skill mechanics | Focus on problems user solves, not CLI/SDK internals |
| **Err on the side of pushy** | Include implicit trigger scenarios explicitly | `even when the user doesn't explicitly mention [product]` |
| **Negative boundaries** | State what the skill is NOT for | `Not for billing, RAM, or related products` |
| **Keep concise** | Under 1024 character hard limit; **target ≤ 600** for buffer | Aim for 300–600 characters |

### Create Eval Queries

Create an `assets/eval_queries.json` file with ~20 queries (10 should-trigger, 10 should-not-trigger):

```json
[
  { "query": "I need to create an [product] instance", "should_trigger": true },
  { "query": "Check my account bill", "should_trigger": false }
]
```

**Query design tips:**
- **Should-trigger**: Vary phrasing (formal/casual/typos), explicitness (names product vs describes need), detail level (terse vs context-heavy)
- **Should-not-trigger**: Focus on **near-misses** — queries sharing keywords but needing different skills
- **Realism**: Include file paths, personal context, casual language, abbreviations

### Optimization Loop

1. **Evaluate**: Run each query through the agent with the skill installed; compute trigger rate
2. **Identify failures**: Which should-trigger queries didn't trigger? Which should-not-trigger did?
3. **Revise**: If too narrow — broaden scope. If too broad — add specificity or negative boundaries
4. **Repeat**: 5 iterations max. Use a 60/40 train/validation split to avoid overfitting.

### Apply the Result

- Update `description` in SKILL.md frontmatter
- Verify under 1024 characters (target ≤ 600)
- Test with 5–10 fresh queries as sanity check

## 2. Generation Telemetry & Observability

Track generation process metrics for continuous improvement:

### Generation Metrics

| Metric | Description | Target |
|--------|-------------|--------|
| **Generation Duration** | Time from Step 1 start to Step 7 complete | < 5 minutes |
| **Feedback Loop Count** | Number of "return to previous step" cycles | ≤ 2 |
| **P0 First-Pass Rate** | Percentage of P0 checks passing on first verification | > 80% |
| **Placeholder Leak Count** | Number of unreplaced `[Placeholder]` strings in output | 0 |
| **Anti-Pattern Hits** | Number of anti-patterns detected in final review | 0 |
| **Eval Query Accuracy** | Trigger rate on should-trigger queries | > 90% |
| **Eval Query Precision** | Non-trigger rate on should-not-trigger queries | > 90% |

### Generation Log Template

```markdown
## Generation Log — ve-[product]-ops

- **Started:** 2026-05-16T10:00:00Z
- **Completed:** 2026-05-16T10:03:45Z
- **Duration:** 3m45s
- **Feedback Loops:** 1 (Step 4 → Step 2: missing error codes)
- **P0 First-Pass:** 24/28 (86%)
- **Placeholders Found:** 0
- **Anti-Patterns:** 0
- **Eval Accuracy:** 18/20 (90%)
- **Generated By:** [agent name]
- **OpenAPI Source:** [URL]
- **CLI Version:** v1.0.42
```

Update the [prompt effectiveness tracking table](prompt-library.md#5-prompt-effectiveness-tracking) monthly based on these metrics.

## 3. Version Pinning Strategy

### CLI Version Pinning

The `ve` CLI version used during generation should be recorded:

```yaml
# In generated skill's metadata or references/integration.md
cli_version_used: "v1.0.42"
cli_version_check_date: "2026-05-16"
cli_latest_available: "auto-detect from https://github.com/volcengine/volcengine-cli/releases"
```

### SDK/API Version Pinning

```yaml
# In generated skill's frontmatter metadata
api_profile: "Volcengine [Product] API v2024-01-01"  # From OpenAPI spec version
sdk_version_minimum: "volc-sdk-golang@v1.0.0"       # If versioned
```

### Version Drift Detection

When OpenAPI or CLI changes:
1. Compare new spec against the `api_profile` pinned in the skill
2. If breaking changes detected → bump skill version, regenerate affected sections
3. Document changes in the skill's Changelog table
