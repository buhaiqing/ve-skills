## 1. Multi-Metric Correlation

### 1.1 Anomaly Pattern Detection

Monitoring skills MUST define ≥ 4 anomaly patterns with detection logic:

| Pattern Name | Metrics Involved | Detection Logic | Severity |
|-------------|-----------------|-----------------|----------|
| CPU-Memory Pressure | CPU usage > 90% + Memory > 85% | AND condition over 5min window | Critical |
| Disk Capacity Warning | Disk usage > 85% AND growth rate > 5%/day | Trend analysis | Warning |
| Network Congestion | Inbound latency > 100ms + Packet loss > 1% | Concurrent threshold | Warning |
| I/O Bottleneck | Disk IOPS > 90% limit + Queue depth > 4 | Sustained for 10min | Critical |

### 1.2 Metric Namespace Convention

Use Volcengine monitoring namespace pattern:
- ECS: `Volcengine_ECS_*`
- RDS: `Volcengine_RDS_*`
- Redis: `Volcengine_Redis_*`

## 2. Cross-Skill Diagnosis Decision Tree

### 2.1 Decision Tree Template

```
[Alarm Triggered]
    │
    ├── Is it CPU-related?
    │   ├── Yes → Is memory also high?
    │   │   ├── Yes → Application-level issue (check logs, GC, threads)
    │   │   └── No → Check for runaway processes (top, ps)
    │   └── No → Continue...
    │
    ├── Is it disk-related?
    │   ├── Disk usage → Check log files, temporary files
    │   └── Disk IOPS → Check database queries, backup jobs
    │
    ├── Is it network-related?
    │   ├── High latency → Check upstream dependencies
    │   └── Packet loss → Check security groups, ACLs
    │
    └── Unknown pattern → Delegate to ve-cms-ops for analysis
```

### 2.2 Delegation Rules

- If the issue spans multiple products, the primary skill delegates to specialized skills
- Document delegation conditions in the skill's Trigger & Scope section
- Never duplicate another skill's full diagnosis flow

### 3.1 Alarm-to-Diagnosis Mapping

| Alarm Source | Primary Diagnosis Skill | Secondary Skill | Fallback |
|-------------|------------------------|-----------------|----------|
| ECS CPU/Memory > 90% | ve-ecs-ops | ve-cms-ops | Manual review |
| RDS Connection > 90% | ve-rds-ops | ve-ecs-ops (app connections) | ve-das-ops |
| Redis Memory > 85% | ve-redis-ops | ve-cms-ops | Manual review |
| VPC Bandwidth > 80% | ve-vpc-ops | ve-slb-ops | Manual review |

### 3.2 Delegation Pattern in Skills

```markdown

- If alarm involves database performance metrics → delegate to `ve-rds-ops`
- If alarm involves container resource limits → delegate to `ve-ecs-ops`
- If alarm origin is unclear → delegate to `ve-cms-ops` for correlation analysis
```

## 4. Proactive Inspection

### 4.1 Inspection Checklist Template

```markdown
## Proactive Inspection — [Date]

### Resource Health
- [ ] CPU usage < 70% across all instances
- [ ] Memory usage < 80% across all instances
- [ ] Disk usage < 80% with > 50GB free space
- [ ] Network error rate < 0.1%
- [ ] Active connections < 80% of limit

### Security Posture
- [ ] No publicly exposed instances without need
- [ ] Security group rules follow least privilege
- [ ] No unused public IP addresses
- [ ] SSL certificates not expiring within 30 days

### Cost Optimization
- [ ] No idle instances (CPU < 5% for 7 days)
- [ ] No unattached volumes
- [ ] No unused EIP addresses
- [ ] Reserved instance coverage > 60%
```

### 4.2 Inspection Automation

Skills SHOULD support automated inspection via:
- Batch describe operations across resources
- Threshold comparison against baseline
- Anomaly flagging with severity classification
- Summary report generation

## 5. Alarm Storm Handling

### 5.1 Storm Detection Criteria

An alarm storm is detected when:
- > 10 alarms within 5 minutes from the same resource group
- > 50% of alarms share the same root cause metric
- Alarm rate exceeds 3x the baseline rate

### 5.2 Storm Suppression Workflow

```
[Storm Detected]
    │
    ├── Step 1: Correlate alarms by resource and time window
    │
    ├── Step 2: Identify the root alarm (earliest or highest severity)
    │
    ├── Step 3: Group related alarms under the root alarm
    │
    ├── Step 4: Suppress duplicate notifications (notify once per root)
    │
    ├── Step 5: Execute root cause diagnosis on the primary alarm
    │
    └── Step 6: After root cause resolution, verify all related alarms clear
```

### 5.3 Notification Throttling

| Storm Level | Throttle Behavior |
|-------------|------------------|
| Mild (10-30 alarms/5min) | Notify once per minute |
| Moderate (30-100 alarms/5min) | Notify once per 5 minutes |
| Severe (> 100 alarms/5min) | Notify once per 15 minutes + escalate |

## 6. Knowledge Base Requirements

### 6.1 Fault Pattern Library

Skills requiring diagnosis capabilities MUST include `references/knowledge-base.md` with:

- ≥ 3 product-specific fault patterns
- ≥ 1 cascade failure pattern (A causes B causes C)
- Each pattern includes: symptoms, root cause, resolution steps, prevention tips

## 7. Multi-Round Diagnosis Review

### 7.1 Three-Round Review Process

| Round | Focus | Critical Questions |
|-------|-------|-------------------|
| **Round 1: Fact Check** | Data accuracy | Are the metrics current? Are thresholds correct? |
| **Round 2: Causal Analysis** | Root cause | Is the identified cause the true root cause? Could something else explain the symptoms? |
| **Round 3: Solution Validation** | Fix effectiveness | Will the proposed fix actually resolve the issue? Could it cause side effects? |

### 7.2 Critical Reflection Questions

Before finalizing diagnosis:
1. What evidence supports this conclusion?
2. What evidence contradicts it?
3. What alternative explanations exist?
4. What would happen if we're wrong?
5. How can we verify the fix worked?
